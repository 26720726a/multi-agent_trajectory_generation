## 2. 무엇을 어떻게 제한했는가

### 2-1. 제한 방식: 클리핑 (탈락이 아니라)

지시서가 **먼저 정하고 근거를 적으라**고 한 부분이다.  후보 65개를 만든 뒤
`|v_cand − v_prev| ≤ a_max·dt = 0.30 m/s` 를 넘는 것만 `v_prev` 쪽으로
끌어당긴다 (`planning/control.py::_candidates`).

* **탈락시키지 않는 이유.**  남는 후보 수가 상황마다 달라지고, 최악에는 하나도
  안 남는다.  그러면 `step` 의 기하 하드 필터가 만드는 정지와 구별할 수 없어
  "기하적으로 막혔다" 와 "가속이 모자랐다" 가 같은 증상으로 뭉개진다.  이 둘을
  갈라 세는 것이 §5 의 핵심이므로 뭉개면 안 된다.
* **클리핑의 대가**는 서로 다른 후보가 같은 값으로 뭉갠다는 것이다.  뭉개진
  후보는 비용도 같아 `argmin` 이 첫 번째를 고른다 — 결정론적이고, 중복을
  제거하지 않으므로 인덱스 대응도 흐트러지지 않는다.
* 넘는 후보만 손댄다.  전부를 `v_prev + (c − v_prev)` 로 재조립하면 제한에
  걸리지도 않은 후보의 마지막 자리가 부동소수 오차로 흔들린다.

### 2-2. 게이트 1 — `a_max = inf` 되돌림

`math.isfinite(dv_max)` 가 거짓이면 클리핑 블록을 통째로 건너뛴다.  그래서
`a_max` 를 `inf` 로 되돌리면 S2 코드와 **완전히 같은 경로**가 돈다.

작업 트리를 건드리지 않으려고 저장소를 스크래치패드로 복사해 거기서만
`a_max=math.inf` 로 바꿔 돌렸다.

```
scripts/s2_regression/compare_traj.py   ->  mismatched arrays: 0
                                            RESULT: IDENTICAL
scripts/check_wm.py 출력 vs 원본 results/check_wm_v0.txt
    md5 e1f2841f2f241abb48c1d11248dc4b6e (양쪽 동일), diff 0줄
```

5종 시나리오 × 3 시드의 `pos`/`vel`/이벤트가 **원본과 비트 단위로 동일**하다.
구현이 옳다는 것을 이것 말고 확인할 방법이 없으므로 이 게이트가 제일 먼저다.

### 2-3. 안전 계층과의 충돌 처리 (§A-2 의 결정 그대로)

* 명령 속도는 `a_max` 로 제한한다 (후보 클리핑).
* `_project_safe` 의 출력은 제한하지 **않는다.**  제한하면 충돌 방지가 깨진다.
* 대신 넘긴 것을 센다.  그런데 "넘겼다" 만 세면 원인이 섞이므로 **배타적으로
  넷으로 갈랐다** — 원인이 다르면 대응이 다르기 때문이다.

| 이름 | 뜻 |
|------|-----|
| `stop` | HOI dwell 진입 / goal 도착으로 속도가 0 으로 강제됨.  **과업 정의**라 감속 구간이 아예 없다 |
| `block` | 후보 65개가 전부 기하 필터에 걸려 강제로 섬.  기하가 원인이지 컨트롤러의 선택이 아니다 |
| `snap` | W/G 정확 착지 대입이 속도를 갈아끼움 |
| `project` | `_project_safe` 가 넘김 — **§A-2 가 재라고 한 숫자** |

## 5. §A-2 의 숫자 — `n_amax_violations`

성공한 3,914행 기준.  **모든 행에 위반이 있다** (0이 아닌 행 3914/3914).

```
    n_amax_violations 합계 26,784   행당 최대 18
      원인 분해 (배타적, 합 = 위 총계)
        정지 (HOI dwell/도착)         10,716  ( 40.0%)
        후보 전멸 (기하)               7,609  ( 28.4%)
        착지 스냅                      8,403  ( 31.4%)
        안전 투영  <- §A-2                56  (  0.2%)
    안전 투영 개입 795,787 표본,  후보 전멸 9,609 표본
```

**가장 중요한 결과다.**  §A-2 는 "이 숫자가 크면 물리적으로 실현 불가능한
회피에 의존하고 있다는 뜻"이라고 적었다.  실제로는 **0.2% 다.**

`_project_safe` 는 795,787 표본에 개입하면서 — 성공 행 전체 표본의 상당 부분이다 —
그중 `a_max` 를 넘긴 것은 56건뿐이다.  **투영은 거의 항상 `a_max` 안에서
문제를 해결한다.**  이유는 투영이 속도를 절반씩 줄이는 방식이라, 후보가 이미
`a_max` 안에 갇혀 있으면 그 절반도 대체로 안에 남기 때문이다 (추론).

따라서 **계획서 §2.3 의 `a_max` 산출을 재검토할 근거는 이 데이터에 없다.**
문제는 회피가 아니라 다른 데 있다.

나머지 99.8% 의 성격:

* **정지 40.0%** — HOI 는 "waypoint 에서 d 초 정지"라는 과업 정의다.
  감속 구간이 모델에 없다.  이건 컨트롤러의 잘못이 아니라 **과업 모델과
  가속도 모델이 서로 모른다**는 뜻이다.
* **착지 스냅 31.4%** — W/G 에 정확히 내려앉으려고 속도를 갈아끼우는 자리
  (`controller.py` 원본 424-426).  같은 성격이다.
* **후보 전멸 28.4%** — 기하 필터가 65개를 전부 기각해 강제로 선 경우.
  9,609 표본에서 후보가 전멸했고, 그중 7,609번이 `a_max` 초과 정지였다.
  **이것이 성능 손실과 직결된다** (§6-1).

## 6. 원인 — 왜 성공률이 떨어졌는가

### 6-1. 후보 팬이 붕괴한다 (확인)

`dv_max = a_max·dt = 0.30 m/s` 다.  후보 65개를 이전 속도 주변 반경 0.30 의
원반 안으로 밀어 넣으면 이렇게 된다.

| `|v_prev|` | 서로 다른 후보 | 서로 다른 속력 | 도달 가능한 속력 범위 |
|---|---|---|---|
| 0.0 | **17 / 65** | **2** | [0.000, 0.300] |
| 0.3 | 45 / 65 | 21 | [0.000, 0.600] |
| 0.6 | 46 / 65 | 22 | [0.300, 0.900] |
| 1.2 | 44 / 65 | 22 | **[0.900, 1.200]** |

두 가지가 치명적이다.

* **정지 상태에서 선택지가 17개, 속력은 {0, 0.3} 둘뿐이다.**  멈춘 에이전트가
  다시 출발할 때 고를 수 있는 것이 거의 없다.  그 17개가 기하 필터에 걸리면
  계속 서 있는다.
* **순항 중(|v|=1.2)에는 0.9 밑으로 못 내려간다.  한 스텝에 멈출 수 없다.**
  `_project_safe` 가 있어 충돌은 안 나지만, 컨트롤러 자신은 "속도를 줄여
  피한다" 는 선택지를 **가지고 있지 않다.**

### 6-2. 감속 프로파일이 없다 (확인 + 추론)

`v_pref` 는 `min(v_lim, d_target/dt)` 로 정해진다 (원본 `controller.py:360`).
`d_target` 이 한 스텝 거리보다 클 때는 항상 최대 속력을 원한다.  물리적으로
맞는 식은 `min(v_lim, d_target/dt, sqrt(2·a_max·d_target))` — 목표에서 멈출 수
있는 속도로 미리 줄이는 것이다.  **그 항이 없다.**

그래서 에이전트는 자기가 지울 수 없는 속도를 낸 뒤, 목표 근처에서
착지 스냅(31.4%)이나 강제 정지(28.4%)로 급정거한다.  실측 덤프에서
`n2_chain_0527f852 ps=1` 의 B 는 0.815 → 0.587 → 0.320 → 0.020 → 0 으로
**매 스텝 정확히 3.00 m/s²** 씩 줄인다 — 상한이 계속 물려 있다는 뜻이다.
(`results/s3/A_incident_n2_chain_0527f852.txt`)

이것은 **S3-A 지시서가 바꾸라고 한 범위 밖**이다.  지시서는 `_candidates` 의
제한만 지정했고 `v_pref` 는 손대지 말라는 취지였다.  고치지 않았다.

### 6-3. 그런데 209건은 좋아졌다 (확인, 예상 밖)

지시서가 "a_max 도입이 성능을 올렸다면 예상 밖이므로 원인을 파고들라"고 한
경우가 부분적으로 발생했다.  기준선에서 실패하던 209건이 A 에서 성공했고,
makespan 도 102건은 빨라졌다 (최대 −7.30s).

**추론**: 기준선의 컨트롤러는 매 스텝 임의의 속도를 고를 수 있어 서로 마주 본
두 에이전트가 진동(왕복)에 빠질 수 있다.  `W_TURN=0.22` 는 그것을 비용으로만
누른다.  `a_max` 는 그 진동의 진폭을 **구조적으로** 제한하므로, 진동성
livelock 이 원인이던 인스턴스는 오히려 풀린다.  얻은 209건 중 101건이 n=4 인
것이 이 해석과 맞는다 (에이전트가 많을수록 진동이 잦다).

**이 추론은 검증하지 않았다.**  검증하려면 얻은 209건에서 기준선 궤적의
속도 부호 반전 횟수를 세면 된다 — S3-B 이후로 미룬다.

### 6-4. `n_switches` 가 늘었다 (확인)

중앙값 1 → 3.  플래너가 재선택을 더 자주 한다.  **추론**: 가속 제한 때문에
같은 mode 라도 실제로 굴러가는 궤적이 계획과 더 크게 어긋나고, 그래서 다음
재계획에서 순위가 뒤집힌다.  히스테리시스(`switch_margin_*`)는 그대로인데
전환이 늘었다는 것은 비용 차이가 실제로 커졌다는 뜻이다.

## 7. 게이트 미달 — 무엇을 정해야 하는가

**코드를 고치지 않았다.**  아래는 관측이지 처방이 아니며, 어느 쪽으로 갈지는
결정이 필요하다.

### 7-1. 확인된 사실 정리

1. 충돌은 0 이다.  **안전은 `a_max` 도입과 무관하게 성립한다.**
2. 안전 투영이 `a_max` 를 넘기는 일은 사실상 없다 (0.2%).
   계획서 §2.3 재검토의 근거는 이 데이터에 없다.
3. 손실은 전부 **deadlock** 이고, 그 뿌리는 후보 팬 붕괴와 감속 프로파일
   부재다.
4. 그럼에도 209건은 새로 풀렸다.

### 7-2. 선택지 (섞지 말고 하나씩, 각각 짝지은 비교로)

| # | 무엇을 | 성격 | 위험 |
|---|--------|------|------|
| A1 | `v_pref` 에 제동 항 `sqrt(2·a_max·d_target)` 추가 | **알고리즘 변경.** 감속 프로파일을 넣는다 | 목표 도달이 느려질 수 있다.  §6-2 가 지목한 뿌리를 직접 건드린다 |
| A2 | `SPEED_LEVELS` 를 `v_prev` 기준 상대 배율로 재정의 | 후보 팬 붕괴를 완화 | 팬의 의미가 바뀐다.  S2 재현이 깨진다 |
| A3 | `dt` 를 0.10 → 0.05 로 | `dv_max` 가 절반이 되지만 스텝이 두 배 | rollout 비용 2배.  1Hz 예산에 직접 영향 |
| A4 | `a_max` 를 3.0 → 더 큰 값으로 | 계획서 §2 목표를 바꾸는 것 | 목표값을 결과에 맞춰 고치는 것이라 §원칙에 반한다 |
| A5 | 게이트 −5%p 를 그대로 두고 **A 를 채택하지 않음** | S3-B 를 a_max=inf 로 진행 | 계획서 §2 를 포기하는 것 |

**측정 없이 고르지 말 것.**  A1 은 §6-2 가 뿌리로 지목한 곳을 직접 건드리므로
가장 근거가 있지만, 그것 역시 "지시서가 정하지 않은 알고리즘 변경"이다.

### 7-3. 함께 보고할 것 — 빨간 테스트 3건

`tests/test_safety.py` 가 `crossing2` 에서 3건 실패한다 (`max_modes=4` 인
FAST 설정).

```
FAILED test_independent_validator_passes[crossing2]
FAILED test_hoi_dwell_is_held[crossing2]
FAILED test_everyone_reaches_the_goal[crossing2]
```

**충돌 관련 테스트는 전부 통과한다** (`test_no_agent_collisions`,
`test_no_obstacle_collisions`, `test_dependency_order_holds`,
`test_speed_limit_never_exceeded`).  즉 **안전은 지켜지고 완주가 깨진다** —
배치 결과와 정확히 같은 그림이다.

이 테스트들을 고치지 않았다.  결과를 보고 게이트를 무르는 일이기 때문이다.
`deadlock2` 는 같은 설정에서 통과한다.

전체 스위트: **214 통과 / 3 실패 / 6 skip**.

## 8. 예상과 달랐던 것

1. **안전 투영은 `a_max` 를 거의 넘지 않는다** (0.2%).  §A-2 는 이 숫자가 클
   것을 전제하고 "숨기지 말고 재라"고 했는데, 재어 보니 작았다.  구조상
   투영이 속도를 **줄이는** 방향으로만 작동하고, 줄어든 값도 이미 좁아진
   후보 범위 안에 남기 때문이다 (추론).
2. **위반의 71.4% 가 과업 정의와 착지 처리에서 나온다.**  `a_max` 를 넣자
   드러난 것은 회피의 문제가 아니라 **HOI 과업 모델에 감속 구간이 없다**는
   것이었다.  S0/S1 의 개념 목록에는 이 충돌이 없었다.
3. **209건이 새로 풀렸다.**  가속 제한이 진동성 livelock 을 구조적으로 막는
   방향으로 작용한 것으로 보인다 (§6-3, 미검증).
4. **`size` 축이 단조롭지 않다** (8.0 −4.26%p, 10.0 −12.78%p, 12.0 −4.88%p).
   이 프로젝트에서 성능 곡선이 단조롭다는 가정이 또 한 번 어긋났다 (P0-3 의
   h=8 정체와 같은 종류).  S3-C 의 "첫 정체점에서 멈추지 않는다" 규칙이
   왜 필요한지 보여준다.
5. **`max_accel` 이 A 에서 정확히 12.00 으로 균일하다.**  중앙값·p90·최대가
   모두 같다는 것은 남은 위반이 전부 "1.20 m/s → 0 을 한 스텝에" 라는 한 가지
   사건이라는 뜻이다 (추론).

## 9. 이번 단계에서 고친 도구 버그

측정 중에 드러난 것들이다.  전부 이 보고서의 수치에 영향을 준다.

1. **`compare_runs.sign_test` 가 격자 전체에서 터졌다.**  `2 ** n` (n≈4,000)이
   float 로 안 옮겨져 `OverflowError`.  로그 공간으로 고쳤고,
   `fractions.Fraction` 으로 짠 기준값과 대조하는 테스트를 추가했다.
   작은 n 으로만 테스트해서 놓친 자리다.
2. **`dump_incident` 가 `uid` 의 첫 행만 읽었다.**  `planner_seed` 가 다른 행의
   메타데이터를 붙여 "CSV 는 성공인데 재현은 실패" 처럼 보였다.  필터를 추가했다.
3. **`pkill -f "python.*bench.run"` 이 자기 셸을 죽였다.**  패턴이 자신의
   명령줄과도 매치되어, 같은 명령 안의 뒤 단계(패치 스크립트)가 조용히 실행되지
   않았다.  이후로는 `ps` 로 PID 를 모아 죽인다.

배치는 두 번 다시 돌렸다.  (1) 계측 열을 기준선과 A 가 같은 스키마로 갖게
하려고, (2) "후보 전멸" 을 "착지 스냅" 에서 떼어내려고.  둘 다 14% 진행
시점에 잡았다.  두 번째 것을 안 고쳤다면 §5 의 원인 분해가 28.4%p 만큼 틀렸다.
