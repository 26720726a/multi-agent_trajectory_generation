## 2. 무엇을 바꿨는가

```python
d_brake = min(d_target, d_geom, d_dep)
v_pref  = ... * min(v_lim, d_target/dt, brake_speed(d_brake))
```

* `d_target` — 현행 그대로 (waypoint/goal 직선거리)
* `d_geom` — 진행 방향 부채꼴로 잰 자유 거리 (§3)
* `d_dep` — 의존성 대기 중이면 `slack = d_target − DEP_STANDOFF`, 아니면 `inf`

`d_target/dt` 항은 **그대로 두었다** (지시서대로).  그것은 오버슛 방지이지
제동이 아니다.

`blocked` / `slack` 계산 두 줄을 `v_pref` 앞으로 올렸다.  둘 다 `phase` 와
`d_target` 만 쓰므로 순서를 바꿔도 값이 같다 (확인 — 게이트 1 이 이를 보증한다).

기존 한 스텝 감속(`if slack < v_lim*dt`)은 **그대로 두었다** (지시서대로).
제동 항이 그 역할을 흡수하므로 **중복**이지만 둘 중 작은 쪽이 이겨 동작은
안전한 방향이다.  제거는 별도 축이다.

### 2-1. 게이트 1 — `a_max = inf` 재현

`brake_speed` 가 `a_max=inf` 에서 곧바로 `inf` 를 내므로, 자유 거리를
**재지도 않게** `math.isfinite(A_MAX)` 로 감쌌다.  재현이 자명하고 비용도 0 이다.

```
compare_traj.py   ->  mismatched arrays: 0 / RESULT: IDENTICAL
check_wm.py 출력 vs 원본 results/check_wm_v0.txt   ->  diff 0줄
```

`tests/test_braking.py::test_infinite_a_max_never_calls_the_distance_probe` 가
"호출조차 되지 않는다"를 지키고 있다.

## 3. `d_geom` 측정 방식 — 세 가지를 시험했다

지시서가 "**먼저 정하고 근거를 보고서에**" 라고 한 부분이다.
**선택 과정에서 5종 시나리오 결과를 봤다는 사실을 먼저 밝힌다.**
지시서 문언은 "진행 방향에서" 였고 그것은 외길 광선인데, 외길이 완주를
깨뜨리는 것을 보고 부채꼴로 바꿨다.  방식 선택은 지시서가 맡긴 범위지만
순서는 그러했다.

| 방식 | 5종 시나리오 (seed=0) | 판단 |
|------|----------------------|------|
| ① 외길 광선 (지시서 문언) | crossing2·fork3 **완주 실패** (tt 12.0 / 16.0) | 굽은 통로에서 과도 감속 — 지시서가 경고한 경우 |
| ② 고정 부채꼴 ±40° | 5종 전부 성공, 위반 A′ 수준 그대로 | 각도가 임의값이라 근거가 없다 |
| ③ **속도 유도 부채꼴** (채택) | 5종 전부 성공, 위반 A′ 수준 | 임의 상수가 없다 |

**③ 을 고른 이유.**  부채꼴 반각을 `asin(dv_max / |v|)` 로 **`a_max` 에서
유도**한다.  한 스텝에 횡으로 쓸 수 있는 속도 변화가 `dv_max = a_max·dt` 뿐
이므로 이것이 **다음 스텝에 실제로 갈 수 있는 방향 범위**다.

| `|v|` | 반각 |
|---|---|
| 1.20 (순항) | 14.5° |
| 0.90 | 19.5° |
| 0.60 | 30.0° |
| ≤ 0.30 | 90° (전방위) |

**왜 최댓값을 쓰는가.**  막으려는 것은 후보 전멸이고, 전멸은 **모든** 방향이
막힐 때만 일어난다.  한 방향이라도 멀리 갈 수 있으면 감속할 이유가 없다.

**왜 반경 검색(`scene.nearest_points`)이 아닌가.**  방향을 보지 않아 옆으로
스쳐 지나가는 벽까지 세므로 **통로 안에서 항상 기어가게** 된다.  광선은
`step()` 의 하드 필터와 **정확히 같은 판정**(`free_steps`)을 쓴다.

### 3-1. 캡 값 — 0.30 m

지시서 권장값 그대로다.  실측 필요량(순항에서 정지까지의 이동거리)
**0.180 m** 의 1.67 배다.  무한정 보면 통로에서 항상 기어간다.

`config/controller.py::brake_lookahead` 에 넣었다.  그래서 **`phys_fp` 가
`2070da06d4a0` → `058289b6e9fe` 로 갈렸다** — S3-A″ §8 이 지적한 "지문이
알고리즘 변경을 못 잡는다" 는 구멍이 이번엔 자동으로 메워졌다.
알고리즘 변경을 config 필드로 표현할 수 있으면 그렇게 하는 편이 낫다는 것을
배웠다 (추론).

### 3-2. 계산 비용 (게이트 5)

`free_steps` 호출 한 번(끝점 5 방향 × 8 지점 = 40개)이 추가된다.
같은 스텝에서 후보 65개에 대해 이미 한 번 부르므로 산술적으로는 62% 증가다.

실측 — 재계획 1회당 벽시계 (성공 행에서만):

| | 중앙값 | p90 |
|---|---|---|
| A′ | 0.2894 s | 0.4627 s |
| A‴ | 0.3815 s | 0.6150 s |
| **배율** | **1.318x** | 1.329x |

**게이트 5 미달** (기준 1.2배).  1 Hz 안에 든 비율은 여전히 100% 이므로
절대 예산은 지키지만, **얻은 것이 없는 32% 증가**다.

## 6. 게이트 4 의 직접 증거 — 반사실 평가 재실행

지시서가 "**이것이 진단이 맞았는지 확인하는 유일한 직접 증거**" 라고 한 부분.
무작위 100 표본에서 S3-A″ §4 와 같은 평가를 다시 돌렸다.

### 6-1. 급정거형 — 소수점까지 같다

| 후보 집합 | A′ (257건) | **A‴ (272건)** |
|---|---|---|
| a) 현행 클리핑 65개 전부 막힘 | 100.0% | 100.0% |
| **b) 도달 가능 원반에 자유** | **0.0%** | **0.0%** |
| c) 클리핑 없는 65개에 자유 | 100.0% | 100.0% |
| d) 즉시 정지(v=0)가 자유 | 100.0% | 100.0% |

**b 가 여전히 0.0% 다.**  처방은 **도달 가능 원반을 조금도 넓히지 못했다**
(확인).  당연하다 — 제동 항은 `v_pref` 를 줄일 뿐 원반의 크기(`a_max·dt`)를
바꾸지 않는다.  원반이 작아서 생긴 문제를 `v_pref` 로 풀 수 없다.

**이것이 게이트 4 미달의 직접 원인이고, 진단이 맞았는지에 대한 답이다:
진단(H2)은 맞았으나 처방이 H2 를 겨냥하지 못했다** (추론).

주의 — 두 표본은 **짝지어지지 않았다.**  `n_blocked > 0` 인 행 목록이 달라
같은 시드로 뽑아도 공통 인스턴스가 100 중 10 뿐이다.  그래도 b/c/d 가 전부
동일한 극단값(0/100/100)이라 표본 차이로 설명되지 않는다.

### 6-2. §5-3 여유 분포 — 이동하지 않았다

지시서가 "중앙값 0.018 m 가 0.18 m 쪽으로 이동했는가" 를 물었다.

| | A′ | **A‴** |
|---|---|---|
| 기하로 막힌 급정거형 | 124건 | 129건 |
| 팽창 경계까지 여유 중앙값 | +0.018 m | **+0.015 m** |
| p90 | +0.123 m | +0.119 m |
| **제동 필요량(0.180 m)보다 좁은 것** | **124/124 (100%)** | **129/129 (100%)** |

**전혀 이동하지 않았다** (확인).  여전히 100% 가 필요량보다 좁은 곳에서
급정거한다.

### 6-3. 딱 하나 움직인 것 — `d_dep`

| | A′ | A‴ |
|---|---|---|
| 의존성 대기로 막힌 급정거형 중 **순항(>0.9) 비율** | 72.2% | **53.1%** |

아니라 그 반대**인데, 이는 표본이 짝지어지지 않은 탓일 수 있다 (추론, 미확정).

## 7. 추가 항목 — 착지 스냅은 방향이 정반대다

S3-A′ §11 이 "성공률과의 연결은 확인되지 않았다" 고 남긴 것을, §6-4 와 같은
층화로 답했다.  재실행 없이 CSV 만으로 했다.

| | 0건일 때 성공률 | 층화 결과 |
|---|---|---|
| 급정거형 전멸 (`n_amax_viol_block`) | **93.0%** | 23/27 층에서 "있음" 이 나쁨, **−12.44%p** |
| 착지 스냅 (`n_amax_viol_snap`) | **42.5%** | 18/20 층에서 "있음" 이 **좋음**, **+46.86%p** |

카운트별 성공률: 스냅 0건 42.5% → 1-3건 80.1% → 4-10건 **87.9%**.

**역인과다** (추론, 그러나 메커니즘이 명확하다).  착지 스냅은 waypoint/goal 에
**실제로 도착해야** 발생한다.  완주하지 못한 인스턴스는 스냅할 기회가 없다.
그래서 "스냅이 많다" 는 "잘 도착했다" 와 같은 말이다.

**스냅을 줄이려는 시도는 목표를 잘못 잡은 것이다.**  S3-A′ 가 위반 총계의
39.4% 라는 이유로 이것을 문제로 본 것은 오독이었다.

두 열의 피어슨 상관은 **+0.314** 로, 따로 해석해도 된다.

## 8. 예상과 달랐던 것

### 8-1. 제동 항이 98.7% 무효였다 (배치 전에 이미 드러남)

5종 시나리오에서 `brake_free_distance` 를 59,267회 호출했는데
**58,486회(98.7%)가 `cap`(0.30 m)을 반환**했다.  걸린 1.3% 도 값이 중앙값
0.037 m 로, **이미 코앞에 벽이 있을 때만** 걸린다.

부채꼴 안 한 방향이라도 0.30 m 열려 있으면 감속하지 않는데, 그런 경우가
거의 전부였다.  전수 배치를 돌리기 전에 게이트 4 미달을 예측할 수 있었다.

### 8-2. `v_pref` 로는 원반을 넓힐 수 없다 — 처방의 구조적 한계

되돌아보면 자명하다.  H2 는 "**도달 가능 원반이 전부 막혔다**" 는 진단인데,
원반의 크기는 `a_max·dt` 로 고정이고 `v_pref` 와 무관하다.  제동 항은
`v_pref` 를 줄일 뿐이므로 **원반을 옮길 수는 있어도 넓힐 수는 없다.**

§6-1 의 `b = 0.0%` 가 그것을 숫자로 보인다.  진단은 맞았고 처방이 빗나갔다.

### 8-3. 광선 다발은 전멸을 예측하지 못한다

광선이 `cap` 을 반환해도 컨트롤러가 실제로 고르는 방향은 VO 비용이 정하며
부채꼴 밖일 수 있다.  그 방향이 막다른 곳이면 다음 스텝에 전멸한다.
**"어느 방향이 열려 있다" 와 "컨트롤러가 그 방향으로 간다" 는 다르다** (추론).

### 8-4. 외길 광선이 완주를 깨뜨렸다

지시서 문언대로 구현했더니 crossing2·fork3 가 완주에 실패했다 (§3).
지시서가 "과도하게 감속시킬 수 있다" 고 미리 경고한 그대로였다.
**경고가 실현될 때 어떻게 대응할지가 정해져 있지 않았고**, 결과를 보고
방식을 바꾸는 판단을 했다.

### 8-5. 착지 스냅의 방향이 반대였다 (§7)

"위반의 39.4%" 라는 크기 때문에 문제로 보였지만, 층화해 보니 **많을수록
성공률이 높다.**  역인과였다.  위반 카운트를 성능 지표로 읽을 때의 함정이다.

### 8-6. config 필드로 넣은 것이 지문 구멍을 메웠다

`brake_lookahead` 를 `config/controller.py` 에 두자 `phys_fp` 가 자동으로
갈렸다.  S3-A″ §8 에서 별도 도구(W5)로 메운 구멍이, **알고리즘 파라미터를
config 로 올리면** 자연히 사라진다.  다음 변경부터 이 패턴을 쓰는 편이 낫다.

## 9. 정리 — 무엇이 확정됐고 다음은 무엇인가

**확정된 것**

1. **처방(제동 대상 확장)은 뿌리를 못 건드렸다.**  게이트 4 가 −3.2% 로
   50% 기준에 한참 못 미치고, 반사실 평가 `b` 가 여전히 0.0% 다.
2. **구조적 이유가 있다.**  H2 는 원반이 작아서 생긴 문제이고, `v_pref` 를
   줄이는 어떤 처방도 원반을 넓히지 못한다 (§8-2).
3. **처방의 절반(`d_dep`)은 작동했다.**  standoff 경계에 순항으로 부딪히는
   비율이 72.2% → 53.1% 로 줄었다.  다만 전체를 움직이지는 못했다.
4. **비용이 32% 늘었다** (게이트 5 미달).  1 Hz 예산은 지키지만 대가가 없다.
5. **착지 스냅은 문제가 아니었다** (§7).  역인과이므로 향후 지표에서
   위반 총계에 섞어 읽지 말 것.
6. 전멸↔실패의 층화 연결은 A‴ 에서도 그대로다 (23/27 층, −12.28%p).

**되돌릴 것인가**

이 변경은 **비용만 늘리고 얻은 것이 없다** (§5-1: makespan 중앙값 0.000,
성공률 p=0.67).  다만 `d_dep` 부분은 실제 효과가 있었고(§6-3), `max_accel`
중앙값도 12.00 → 9.98 로 낮아졌다.  **되돌릴지 남길지는 다음 시도의 방향이
정해진 뒤에 판단하는 편이 낫다** — `d_geom` 만 떼고 `d_dep` 를 남기는
선택지도 있다 (그것 역시 별도 축이므로 여기서 하지 않았다).

**다음에 재야 할 것**

원반이 좁아서 생긴 문제이므로 원반 쪽을 건드려야 한다.  후보:

| # | 무엇을 | 성격 | 위험 |
|---|--------|------|------|
| B1 | `dt` 0.10 → 0.05 | 원반은 그대로지만 **스텝당 이동거리가 절반**이라 막다른 곳에 덜 깊이 들어간다 | rollout 비용 2배.  게이트 5 를 더 크게 깬다 |
| B2 | 하드 필터를 **다단계**로 (4 스텝 앞까지 후보를 굴려 검사) | H2 를 정면으로 겨냥 | 비용이 크다.  S3-A″ 가 "다단계 전방 검사" 로 지목한 것 |
| B3 | 전멸 시 `v_cmd = 0` 대신 **`a_max` 안에서 최대 감속** | 급정거를 물리적으로 가능하게 만든다.  전멸 자체는 안 줄지만 위반은 준다 | 충돌 위험 — `_project_safe` 가 받아야 한다 |
| B4 | `a_max` 를 3.0 보다 크게 | 원반을 직접 넓힌다 | 계획서 §2 목표를 결과에 맞춰 고치는 것 |

**S3-A″ §9 가 남긴 질문도 여전히 열려 있다**: 급정거형 전멸이 0건인데도
실패하는 7.0% 는 무엇 때문인가.  전멸을 고쳐도 그만큼은 남는다.
