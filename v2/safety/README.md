# safety/ — 무엇이 무엇을 보장하는가

계획서 §1.2 는 "기하 필터가 물리적으로 보장한다" 를 핵심 주장으로 삼는다.
그 주장이 성립하는 **정확한 범위**를 여기 적는다.  범위를 적지 않으면
"보장한다" 는 말은 검증할 수 없고, 실제로 S3 에서 그 경계를 넘는 변경이
안전을 깨뜨렸다 (아래 §4).

---

## 1. 두 가지 안전, 두 개의 장치

| 무엇을 | 누가 | 어디서 | 성격 |
|--------|------|--------|------|
| **에이전트 간 충돌** | `safety/project.py::_project_safe` | 후보 선택 **뒤**, 매 스텝 | 사후 투영 — 어떤 명령이 오든 받아서 고친다 |
| **장애물·벽 충돌** | `planning/control.py::SceneCache.free_steps` | 후보 선택 **전**, 하드 필터 | 사전 배제 — 통과한 후보만 고를 수 있다 |

**둘은 성격이 다르다.**  전자는 무엇이 들어와도 안전하게 만드는 장치이고,
후자는 안전하지 않은 것을 애초에 못 고르게 하는 장치다.  이 차이가 §4 의
결론을 낳는다.

의존성 순서(HOI 선후)는 안전이 아니라 과업 정의이며 `step()` 의
`DEP_STANDOFF` 블록과 `validate` 가 나눠 다룬다.

---

## 2. `_project_safe` — 에이전트 간만 본다

```python
for i in range(n):
    for j in range(i + 1, n):
        R = problem.min_sep(i, j)
        d = seg_seg_min_dist(pos[i], pos[i] + v[i]*dt, pos[j], pos[j] + v[j]*dt)
        ...
```

* 보는 것: **쌍 (i, j) 의 스윕 세그먼트 최근접 거리**뿐이다.
* **장애물은 이 함수에 존재하지 않는다.**  `Rect` 도 `scene` 도 인자에 없다.
* 종료성: 정지는 항상 안전한 배치에서 출발하므로(그 불변식을 이 함수 자신이
  유지한다) 전원 정지가 유효한 fallback 이고, 그래서 루프가 반드시 끝난다.

`tests/test_braking.py::test_the_safety_projection_does_not_cover_obstacles`
가 이 사실을 소스에서 직접 확인한다 — 문서와 테스트가 서로를 가리킨다.

## 3. `free_steps` — 장애물·벽을 막지만, 우회할 수 있다

후보 65개를 벡터화 Liang-Barsky 로 걸러 **팽창 장애물을 지나는 후보를
전부 버린다.**  `step()` 은 통과한 것 중에서만 고른다.

문제는 그 다음이다.

```python
keep = scene.free_steps(i, pos[i], step_pts)
if not np.any(keep):          # 전부 걸렸다 = "후보 전멸"
    v_cmd[i] = 0.0            # <- 이 경로는 필터를 거치지 않는다
    continue
```

**전멸 fallback 은 필터 바깥에 있다.**  현재는 `v_cmd = 0` 이라 위치가 그대로여서
안전하지만, **여기서 조금이라도 움직이게 만들면 아무도 막지 않는다.**

---

## 4. 실제로 깨진 적이 있다 — S3-B3

`reports/S3B3_decel_fallback.md`.  전멸 fallback 을 "즉시 정지" 에서
"`a_max` 로 감속" 으로 바꿨다.  사양(계획서 §3.3-7)에는 맞지만:

```
     t  |v_prev|  |v_cmd|  전멸      장애물거리   여유(radius 0.30)
    64     1.200    0.900  True      0.3259     +0.0259    <- 전멸 시작
    65     0.900    0.600  True      0.2844     -0.0156 !!
    67     0.300    0.000  True      0.2436     -0.0564 !!
```

전수 배치에서 **장애물/벽 침범 88행 (1.81%)**, 최악 `obstacle_clearance`
0.2436 m.  에이전트 간 충돌은 0 이었다 — `_project_safe` 가 막았기 때문이다.

**교훈: "전멸했는데 계속 움직이는" 처방은 전부 같은 문제를 만든다.**
움직이게 하려면 그 움직임도 `free_steps` 를 통과해야 한다.

## 5. 판정의 단일 출처 — `validate.py`

침범 여부는 **오직** `safety/validate.py` 가 정한다.  플래너 내부를 전혀 보지
않고 실행된 좌표만 읽으므로, 플래너가 자기 채점을 하지 않는다.

| 대상 | 하한 | 여유 |
|------|------|------|
| 에이전트 쌍 | 중심거리 ≥ `min_sep(i,j)` = 0.70 | 1e-3 m |
| 장애물·벽 | 중심~경계 ≥ `robot_radius` = 0.30 | 1e-3 m |

여유 1e-3 m 의 근거: 원본 검증기가 쓰던 값이고, `dt=0.1 s` 에서
`v_max=1.2 m/s` 로 한 스텝이 0.12 m 이므로 그 **1/120** 이다.  수치 잡음보다
크고 물리적으로는 무시할 수 있다.

에이전트 쌍은 **스윕**(연속 시간)으로, 장애물은 4배 조밀화한 궤적으로 본다.
샘플 사이를 스쳐 지나가는 충돌을 놓치지 않기 위해서다.

### 쓰는 쪽에서 지킬 것

* **판정에는 `n_agent_violations` / `n_obstacle_violations` 를 쓴다.**
* `status == "invalid"` 를 쓰지 말 것.  `bench/run.py` 가 완주 실패면
  `"unfinished:..."` 로 덮어써서 **항상 0 이다.**  이것을 충돌률로 읽어
  "충돌 0건" 게이트를 네 번 통과시킨 적이 있다 (S3-B3 §7-1).
* clearance 열은 **얼마나 아슬아슬했는지**를 볼 때만 쓴다.  판정은 위 두 열이다.

`tests/test_violation_detection.py` 가 "지표가 실제로 잡는가" 를 고의 침범
궤적으로 확인한다.  탐지가 살아 있는 것과 오탐이 없는 것을 **둘 다** 본다 —
한쪽만으로는 "0건" 이 *안 일어났다* 인지 *못 잡는다* 인지 구별할 수 없다.

## 6. 계층 규칙

`safety/` 는 `planning/` 을 import 하지 않는다
(`tests/test_layering.py::test_safety_does_not_import_planning`).
그래야 "안전은 계획 품질과 무관하게 성립한다" 가 문서가 아니라 구조적 사실이
된다.  `validate.py` 가 `Problem` / `Solution` 을 전방 참조로만 쓰는 이유이고
(S2 §3-1), `vo.py` 가 `problem` 을 덕 타이핑으로 받는 이유다.

---

## 7. 파일

```
geometry.py   2D 기하 — 사각형, 스윕 최근접 거리, 폴리라인
phase.py      과업 단계 상수.  안전 계층이 "움직여 달라고 할 수 없는" 대상을 알아야 한다
project.py    _project_safe — 에이전트 간 상호 안전 투영
vo.py         속도 장애물 비용 (soft).  후보를 **기각하지 않는다** — 비용만 매긴다
validate.py   독립 검증기.  판정의 단일 출처
```

`vo.py` 가 soft 라는 점이 중요하다.  이웃 에이전트는 하드 필터에 **없으므로**
후보 전멸의 원인이 될 수 없다 (S3-A″ §3-3 에서 실측 확인 — 전멸 시점의 이웃
거리 중앙값이 3.08 m 였다).
