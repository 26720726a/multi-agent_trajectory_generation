## 2. `d_target` 의 현행 정의 — 확인하고, 바꾸지 않았다

지시서가 먼저 확인하라고 한 부분이다.  현행 코드 (`planning/control.py`):

```python
leg       = routes[i].leg1 if phase[i] == PHASE_TO_WP else routes[i].leg2
target_pt = a.waypoint    if phase[i] == PHASE_TO_WP else a.goal
d_target  = ||target_pt - pos[i]||          # 유클리드 직선거리
```

* **목표는 phase 에 따라 갈린다.**  `PHASE_TO_WP` 면 waypoint, `PHASE_TO_GOAL`
  이면 goal 이다.  지시서가 요구한 "dwell 예정이면 waypoint 까지" 는 **이미
  만족되어 있다.**  둘 다 속도 0 으로 도착해야 하는 지점이다 — waypoint 는
  `PHASE_DWELL` 로 넘어가며 dwell 동안 정지하고, goal 은 `PHASE_DONE` 에서
  `vel[i] = 0` 이 된다.  그래서 **바꾸지 않았다.  축이 하나도 늘지 않았다.**
* **직선거리이지 경로 호길이가 아니다.**  `leg.remaining(idx)` 라는 호길이가
  같은 함수 안에 있는데도 `d_target` 은 직선거리를 쓴다.  장애물을 돌아가야
  하면 실제 주행거리가 더 길므로, 제동 항 `sqrt(2·a·d_target)` 은 **필요보다
  일찍·강하게 감속**한다.  보수적인 쪽으로 틀리므로 안전하고, 그대로 두었다.
  호길이로 바꾸는 것은 별도의 축이므로 여기서 하지 않았다 (§9-2).

또 하나 그대로 둔 것: 의존성 대기(`DEP_STANDOFF = 0.45 m`) 블록은 제동 항
**뒤에** 오고 기준점이 waypoint 앞 0.45 m 다.  제동 항은 waypoint 자체를
기준으로 하므로 이 둘은 서로 다른 지점을 향해 감속한다.  건드리지 않았다 (§9-3).

## 3. 변경한 것 (전부)

```python
def brake_speed(d_target: float) -> float:
    if not math.isfinite(A_MAX):
        return math.inf
    return math.sqrt(2.0 * A_MAX * max(d_target, 0.0))

v_pref = (aim - pos[i]) / d_aim * min(v_lim, d_target / dt, brake_speed(d_target))
```

`a_max = inf` 일 때 **곧바로** `inf` 를 돌려준다.  `2 * inf * 0.0` 은 `nan` 이고,
`min(v_lim, d/dt, nan)` 은 파이썬에서 `nan` 을 낼 수 있어 S2 재현이 조용히
깨진다.  이 분기가 없으면 `d_target = 0` 인 스텝 하나로 전체가 무너진다.

건드리지 않은 것: `SPEED_LEVELS`, `_candidates`, 안전 계층
(`safety/project.py`, `safety/vo.py`), 착지 스냅 블록, 의존성 대기 블록.

### 6-1. 왜 착지 스냅이 늘었는가

먼저 **내가 세운 첫 가설은 반증됐다.**  "제동 항 때문에 목표 근처에서 느려지니
착지 구간에 더 오래 머물고, 그래서 스냅이 더 자주 발동한다" 고 예상했는데,
실측은 반대였다 (목표 0.12 m 이내 체류 스텝, 5종 시나리오 seed=0):

| 시나리오 | 체류 (제동 없음) | 체류 (제동 있음) | 스냅 위반 (없음 → 있음) |
|---|---|---|---|
| chain3 | 117 | **102** | 2 → 4 |
| fork3 | 119 | **101** | 3 → 6 |
| corridor2 | 64 | **55** | 3 → 2 |
| crossing2 | 75 | 80 | 0 → 0 |
| deadlock2 | 46 | 50 | 1 → 2 |

체류는 오히려 **줄었다** (더 빨리 도착하므로).  그런데 스냅 위반은 늘었다.
즉 **체류 시간이 아니라 발동률이 올랐다.**

스냅 조건은 둘이다 (`planning/control.py`, 원본 `controller.py:424-426`):

```python
if d_target <= v_lim*dt + 1e-12 and \
        ||pos + v_cmd*dt - target|| < ctrl_snap(dt, v_lim):     # = 0.02 m
    v_cmd[i] = (target_pt - pos[i]) / dt
```

**두 번째 조건이 핵심이다.**  제동 항이 없으면 목표 0.12 m 앞에서도 명령 속도가
크고, 한 스텝 가면 목표를 훌쩍 지나쳐 `< 0.02 m` 가 성립하지 않는다.  제동 항이
있으면 명령 속도가 목표에 딱 맞게 줄어들어 **한 스텝 뒤 위치가 목표에 정확히
내려앉고, 그래서 조건 2가 훨씬 자주 성립한다** (추론 — 위 표의 "체류는 줄고
발동은 늘었다" 와 정합적이다).

**제동 항이 궤적을 목표에 더 잘 맞춰 놓자, 그 결과로 정확 착지 대입이 더 자주
발동한 것이다.**  그리고 그 대입은 `a_max` 를 전혀 보지 않는다.

위반의 **크기**는 바뀌지 않았다 (5종 × 3시드, 스냅 위반만 모아서):

| | 건수 | 중앙값 | 평균 | p90 | 최대 | 초과분 합 |
|---|---|---|---|---|---|---|
| 제동 없음 (A) | 27 | 3.94 | 3.91 | 4.68 | 4.81 | 24.6 |
| 제동 있음 (A') | 36 | 3.97 | 3.91 | 4.44 | 4.94 | **32.6** |

**"더 자주, 같은 크기"** 다 (확인).  스냅 경로는 제동 항으로 개선되지 않는다.

### 6-2. `max_accel` 이 여전히 12.00 인 이유 — 이번에 처음 확인

A 와 A' 모두 `max_accel` 중앙값·p90·최대가 전부 12.00 = `v_max/dt` 다.
제동 항이 이 값을 절반으로 줄일 것으로 예상했는데(§7) 그러지 못했다.

`trace` 로 위반 스텝을 직접 들여다보니 최악값의 출처가 분명하다.

```
crossing2: t=35  agent 1  직전속력 1.200 -> 명령 0.000   |dv|/dt 12.00  phase=0  투영전0=True
chain3   : t=110 agent 2  직전속력 1.200 -> 명령 0.000   |dv|/dt 12.00  phase=0  투영전0=True
fork3    : t=26  agent 0  직전속력 1.200 -> 명령 0.000   |dv|/dt 12.00  phase=0  투영전0=True
```

`투영전0=True` 는 `_project_safe` **이전에 이미 명령이 0** 이었다는 뜻이다.
`phase=0` 은 waypoint 로 가는 중, 즉 목표 근처가 아니다.  이것은
**기하 하드 필터의 강제 정지**다:

```python
keep = scene.free_steps(i, pos[i], step_pts)
if not np.any(keep):
    v_cmd[i] = 0.0          # 후보 65개가 전부 기각 -> 무조건 정지
```

순항 속력 1.2 로 달리다 후보가 전멸하면 **한 스텝에 0 이 된다.**  제동 항은
목표 근처에서만 작동하므로 이 경로에 아무 영향이 없고, `a_max` 클리핑도
"후보를 만드는" 단계라 "후보가 전부 기각된 뒤의 fallback" 에는 닿지 않는다.

**즉 `max_accel` 을 지배하는 것은 §6-1 의 팬 붕괴 계열 문제이지 감속
프로파일이 아니다.**  S3-A 는 "후보 전멸 28.4%" 라는 비율까지만 보였는데,
최악값을 만드는 것이 바로 이 경로라는 것은 이번에 확인했다.

## 9. 예상과 달랐던 것

### 9-1. 제동 항은 급정거를 절반으로 줄일 뿐이다 — dt 이산화 (테스트 작성 중 발견)

연속시간에서 `sqrt(2·a·d)` 는 정확히 `a` 로 감속하는 프로파일이다.  `dt` 로
끊으면 목표 바로 앞에서 `d/dt` 항이 제동 항을 이긴다.

```
d/dt < sqrt(2·a·d)   <=>   d < 2·a·dt² = 0.060 m
```

그 구간의 감속도는 `d/dt²` 이고 경계 `d = 0.060 m` 에서 최대가 되어 정확히
**2·a_max = 6.0 m/s²** 다.  제동 항이 없을 때의 최악은 `v_max/dt = 12.0` 이므로
**정확히 절반**이다.  결함이 아니라 지시서가 지정한 식(`sqrt(2·a_max·d_target)`)
을 이산 시스템에 그대로 넣은 결과다.  `tests/test_braking.py` 가 이 수치
(6.0, 경계 0.060)를 못 박았다.

**그런데 실측 `max_accel` 은 12.00 그대로였다** — §6-2 가 보인 대로 최악값의
출처가 착지가 아니라 기하 강제 정지였기 때문이다.  즉 이 이산화 한계는
실제로는 병목이 아니었다.

### 9-2. 효율은 좋아졌는데 성공률이 안 움직였다

makespan(p≈0), `wait`(−9.9%), `n_switches`(−17.7%), `ratio_to_bound`
(1.169→1.133), 시드 간 편차(3.39%→2.00%) 가 전부 개선됐다.  그런데 성공률은
−0.25%p, p=0.57 이다.  **"빠르고 매끄럽게 실패한다"** 는 뜻이다 —
성공/실패를 가르는 것은 감속 프로파일이 아닌 다른 축이라는 강한 신호다 (추론).

### 9-3. 착지 스냅이 늘었다

§6-1.  변경이 노린 두 항목 중 하나가 반대로 움직였고, 그것이 총계를 밀어올렸다.
원인은 "제동 항이 궤적을 목표에 잘 맞추자 스냅 발동 조건이 더 자주 성립한 것"
으로 보인다.  **스냅 자체가 `a_max` 를 보지 않는다**는 것이 뿌리다.

### 9-4. 물리 지문이 이 변경을 잡지 못한다 — 도구의 구멍

`A2_braking.csv` 의 `phys_fp` 가 `A_amax3.csv` 와 **같다** (`2070da06d4a0`).
제동 항은 config 값이 아니라 알고리즘이므로 지문에 잡히지 않는다.
`compare_runs.py` 는 두 파일을 비교하며 "**같다** (같은 물리끼리의 비교)" 라고
출력하는데, 실제로는 알고리즘이 다르다.

이 두 CSV 를 가르는 유일한 열은 `git_commit`(`fb5c257` vs `aca1a47`)이다.
S0 §G-3 위험 3 대응의 구멍이고, 지문에 코드 버전을 넣는 것은 별도의 축이라
지금 고치지 않았다.  **비교할 때 `git_commit` 을 함께 볼 것.**

## 10. §6-3 검증 — 진동성 livelock 추론 (지시서의 추가 확인 항목)

S3-A §6-3 의 미검증 추론: "가속 상한이 진동성 livelock 을 구조적으로 막아
209건이 새로 풀렸다".  A' 에서도 baseline 대비 **188건**을 얻었으므로 표본이
있다.  기준선 물리(`a_max=inf`)로 재실행해 속도 부호 반전을 셌다
(`scripts/count_reversals.py`, 각 군 40개, 100 (에이전트×스텝) 당).

| 군 | n | 중앙값 | 평균 | p90 | 최대 |
|----|---|--------|------|-----|------|
| 얻음 (실패 → 성공) | 40 | **1.012** | 1.445 | 3.889 | 5.833 |
| 양쪽 성공 | 40 | **0.820** | 1.267 | 2.970 | 4.511 |
| 잃음 (성공 → 실패) | 40 | 0.923 | 1.634 | 4.065 | 6.129 |

**방향은 추론과 같다** (얻은 쪽이 더 많이 진동했다).  그러나 **강하게 지지하지는
않는다**:

* 차이가 작다 (1.012 vs 0.820).
* **"잃음" 군도 0.923 으로 양쪽성공보다 높다.**  진동이 성공/실패를 가르는
  변수라면 잃은 쪽은 낮아야 자연스러운데 그렇지 않다.
* 세 군의 분포가 크게 겹친다 (p90 이 2.97~4.07 로 서로 포개진다).
* 짝지어지지 않은 비교이고 각 40건이다.

**결론: 진동 가설은 기각되지도 확증되지도 않았다.**  방향만 맞고, 이 표본으로는
결론을 내지 못한다.  더 판단하려면 반전 횟수를 인스턴스 난이도로 보정하거나
표본을 크게 늘려야 한다 — 게이트 항목이 아니므로 여기서 멈춘다.

## 11. 게이트 3 미달 — 다음에 무엇을 할 것인가

지시서가 미리 정해 둔 대로 **A2(SPEED_LEVELS 상대화)가 다음 후보**다.
이번 결과가 그 판단을 뒷받침한다.

1. 제동 항은 **의도한 축에서 실제로 작동했다** — `wait`, `n_switches`,
   makespan, `ratio_to_bound` 가 전부 유의하게 개선됐다.  그런데 성공률은
   전혀 움직이지 않았다 (p=0.57).
2. `max_accel` 의 최악값은 **기하 하드 필터의 강제 정지**에서 나온다 (§6-2).
   순항 중 1.2 → 0 이고, 이것은 감속 프로파일과 무관하다.
3. 후보 팬 표는 **한 칸도 안 바뀌었다** (§7).  순항 중 도달 가능한 속력이
   `[0.9, 1.2]` 뿐이라는 성질이 그대로다 — 즉 컨트롤러는 여전히 "속도를 줄여
   피한다" 는 선택지를 갖고 있지 않다.

**셋을 합치면 팬 붕괴가 성공률의 독립적인 원인이라는 결론이 된다.**
S3-A 보고서 §7-2 의 A2 가 바로 그 축이다.

곁들여 보고할 것: **착지 스냅이 `a_max` 를 보지 않는다** (§6-1).  A2 와는 다른
축이고, 위반 총계의 39.4% 를 차지하지만 성공률과의 연결은 확인되지 않았다.
