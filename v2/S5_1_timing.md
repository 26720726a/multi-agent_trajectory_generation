# S5-1 — 재계획 타이머 계측 최종 보고

## 결론

S5-0의 `runtime_s / team_time` 91.30%는 재계획 지연의 측정값이 아니었다. 재계획 루프 안에서 후보 생성, rollout, 비용 계산, 선택만 직접 재었다.

**확인:** 단독 실행 표본에서 3,815회 재계획 중 1초 초과는 **0회**였다. 인스턴스별 재계획 중앙값의 중앙값은 140.46 ms, p90은 218.70 ms, 모든 인스턴스에서 관측된 최대는 702.30 ms였다.

**확인:** 같은 표본을 15워커로 돌리면 중앙값은 285.00 ms, p90은 457.90 ms, 최대는 1,845.20 ms이며 3,815회 중 175회(4.59%)가 1초를 넘었다. 병렬 실행의 CPU 경합 수치는 처리량 참고값이지 실시간성 KPI가 아니다.

## 계측 범위와 불변성

계측 범위는 `planning/execute.py` 재계획 loop의 `WorldModel.rollouts` 시작부터 mode 선택까지다. 초기 A* 경로 라이브러리, 문제 생성, 실행 구간 재시뮬레이션, 안전 검증, 시각화는 제외했다.

CSV에는 `n_replans`, `n_replans_over_1s`, `replan_ms_median`, `replan_ms_p90`, `replan_ms_max`를 추가했다. config 값이 아니므로 `phys_fp`는 유지하고 commit으로 코드 버전을 구분한다.

계측 전 h=10 기준 commit `950e503`과 계측 commit `b6767bd`에서 5 시나리오 × 3 seed의 `pos`, `vel`, `done`, `wp_in`, `wp_out` 배열 SHA-256은 모두 `b56ca9ac16430f63527fe74afbaec88bd745096b2968665f2014c0b625b51d4f`로 일치했다. 즉 계측은 궤적을 바꾸지 않았다.

## 표본 한계와 게이트

`bench.run --limit 100`은 생성 격자의 앞쪽 100개를 취했다. 그 순서가 n=2를 먼저 소진하므로 두 배치 모두 **n=2 인스턴스 100개**만 포함했다. 따라서 요청된 n=2/3/4별 재계획 분포는 아직 측정되지 않았다.

이는 재계획 타이머 자체의 게이트(단독 1초 초과 비율 보고, 궤적 불변)에는 영향을 주지 않는다. 그러나 N 확장 예측의 근거라는 A-4 요구사항은 충족하지 못했다. 이 보고서는 n=2 결과만을 최종 사실로 기록하며 n=3/4에 일반화하지 않는다.
