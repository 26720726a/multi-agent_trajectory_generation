# S6-3 — 진단: canonical 을 못 이기는 지배 원인 가르기

표기: **확인** = 측정한 것 / **추론** = 측정에서 끌어낸 판단.
이번 단계는 진단이다. `learn/`·`config/`·알고리즘 코드를 수정하지 않았다.

## 요약

- **게이트 2 의 사전 규칙을 그대로 적용하면 (a) 특성 충돌이 지배적 원인으로
  확정된다** — 충돌 쌍 중 `loss_max` 가 다른 비율이 train 20.6 % / val 13.9 % /
  test 10.3 % 로 **세 split 모두 10 % 이상**이다. 규칙대로 기록한다.
- **그러나 규칙 밖에서 잰 값 세 개가 그 판정을 정면으로 반박한다** (확인).
  가장 결정적인 것: **모델이 보는 특성만으로 완벽하게 고를 때의 regret 이
  val 0.00034 m** 다. 모델의 실제 regret 은 1.135 m 다. **충돌은 도달 가능한
  regret 의 0.03 % 밖에 막지 못한다.**
- **게이트를 고치지 않는다.** 규칙의 분모가 "충돌 쌍"이라 **충돌이 얼마나
  드문지**(전체 쌍의 0.23~0.29 %)를 볼 수 없는 구조였다. 규칙 판정과 반박
  근거를 **둘 다** 남긴다.
- **D2 (용량 축소, d_model 32 / 1층, 파라미터 434,948 → 24,260):
  train↔val 격차는 거의 사라졌다** (tau-b 격차 0.072 → 0.006, regret 격차
  0.218 → 0.009 m). **그런데 val/test 성능은 그대로다** (val regret
  1.135 → 1.159, test 1.100 → 1.026). 즉 과적합을 없애도 얻는 것이 없다.
- **추론: (a) 도 (b) 도 구속 조건이 아니다.** 정보는 특성 안에 있고(오라클
  ≈ 0), 용량을 줄이면 격차는 닫히지만 이득이 없다. 남는 설명은 **표현**이다 —
  `route` 원핫은 "몇 번 경로냐"만 말할 뿐 그 경로가 어디로 도는지를 담지
  않아, 장면을 건너 일반화할 근거가 없다 (§4).

## 1. D1-1 — mode 디코드 vs 토큰 필드 대조

전체 대조표는 `results/s6_3/token_field_audit.md` 에 있다. 요지 세 줄:

1. **`PlanMode` 의 필드는 4개가 전부다** — `routes`, `yield_rank`,
   `cautious`, `split_side` (`planning/worldmodel.py:58`). `label()` 은 이
   4개를 손실 없이 인코딩하고 `learn/data.py:37 parse_mode()` 는 완전히
   역변환한다. **디코드되지 않고 버려지는 mode 필드는 없다** (확인).
2. **지시서가 든 "속도 프로파일 A/B/C"와 "횡 오프셋 폭 ±0.80/±1.20 m"는
   이 구현에 없다** (확인). `cautious` 는 이진값이고 배율은 0.75 고정
   (`worldmodel.py:85`), `split_side` 도 이진값이며 세기는 전역 상수
   `W_SIDE = 0.16` 이다 (`config/controller.py:50`). mode 문자열의
   `B>A>C>D` 는 속도 프로파일이 아니라 **에이전트 이름의 양보 순서**다.
   **추론: 계획서 §3.2 의 mode 공간과 구현이 표본하는 mode 공간이 다르다.**
3. **토큰이 빠뜨리는 것은 mode 필드가 아니라 클러스터 밖 에이전트다.**
   토큰은 구성원 슬롯만 채우는데(`learn/data.py:107`) rollout 은 전원 합동이다.
   **클러스터가 전체의 부분집합인 그룹이 train 78.7 % / val 70.3 % / test 69.9 %**
   다 (확인).

## 2. D1-2 — 충돌률 (핵심 측정)

같은 그룹 안에서 **모델 입력이 완전히 같은** 두 후보를 "충돌 쌍"으로 센다.
후보를 구별하는 칸은 구성원별 `route 원핫(4) + rank(1)` 과 CLS 의
`cautious, split` 뿐이다 (나머지 차원은 S6-2 §0 에서 그룹 내 불변임을 확인).

| 측정 | train | val | test |
|---|---:|---:|---:|
| 그룹 수 | 5,937 | 1,271 | 1,274 |
| 충돌 쌍이 1개 이상 있는 그룹 비율 | **20.9 %** | **19.9 %** | **23.9 %** |
| 그룹당 평균 충돌 쌍 수 | 0.279 | 0.289 | 0.343 |
| *(참고) 전체 쌍 대비 충돌 쌍 비율* | *0.23 %* | *0.24 %* | *0.29 %* |
| **충돌 쌍 중 `loss_max` 가 다른 비율** | **20.6 %** | **13.9 %** | **10.3 %** |
| 충돌 쌍 \|Δloss\| 중앙값 (전체 충돌 쌍) | 0.000 | 0.000 | 0.000 |
| 충돌 쌍 \|Δloss\| p90 (전체 충돌 쌍) | 0.448 | 0.249 | 0.050 |
| \|Δloss\| 중앙값 (다른 쌍만) | 0.411 | 0.548 | 0.200 |
| \|Δloss\| p90 (다른 쌍만) | 3.898 | 3.147 | 3.686 |
| \|Δloss\| 최대 (다른 쌍만) | 7.425 | 6.019 | 5.425 |

**충돌의 원인 분해 — 전부 클러스터 밖이다** (확인):

| 충돌 쌍의 원인 | train | val | test |
|---|---:|---:|---:|
| 클러스터 **밖** 에이전트의 route 가 다름 | 1,655 | 363 | 434 |
| 클러스터 **밖** 에이전트의 rank 가 다름 | 441 | 45 | 67 |
| 밖도 전부 같음 (원리적으로 같은 mode) | **0** | **0** | **0** |

**확인:** 충돌 쌍 100 % 가 "클러스터 밖 에이전트의 계획이 다른데 토큰은
그것을 안 보여주는" 경우다. route 색인이 잘려서 생긴 충돌은 0 건이다 —
mode 문자열의 최대 route 색인이 **3** 이고 원핫 칸도 4 라 `min(route, 3)` 이
자르는 것이 없다 (확인).

`results/s6_3/collision_examples.json` 의 대표 예 (train, k=2, n=3,
구성원 [0,1]):

| mode A | mode B | 다른 곳 | loss_max A | loss_max B |
|---|---|---|---:|---:|
| `r000\|A>B>C` | `r003\|A>B>C` | 비구성원 에이전트 2 의 route (0 vs 3) | 7.104 | **0.000** |

**추론: 충돌이 발생할 때 그 영향은 작지 않다** (7.1 m 차이). 문제는 발생
빈도다 — 전체 쌍의 0.24 % 다.

## 3. 규칙 밖 측정 — 충돌이 실제로 막고 있는 regret

충돌률만으로는 "그래서 regret 이 얼마나 막혔는가"를 알 수 없다. **모델이
보는 특성만 쓰는 완벽한 선택자**의 regret 을 직접 계산했다
(`results/s6_3/feature_oracle.json`). 같은 특성 튜플의 후보들은 구별할 수
없으므로 하나의 동치류로 묶고, 동치류를 골랐을 때의 기대 regret 을 쓴다.

| 비퇴화 그룹 기준 | train (n=4,590) | val (n=878) | test (n=913) |
|---|---:|---:|---:|
| 특성-오라클 regret — 낙관(동치류 안 최소) | 0.0000 | 0.0000 | 0.0000 |
| **특성-오라클 regret — 중립(동치류 안 평균)** | **0.0014** | **0.00034** | **0.00011** |
| 특성-오라클 regret — 비관(동치류 안 최대) | 0.0017 | 0.0005 | 0.0001 |
| 오라클 regret 이 정확히 0 인 그룹 비율 | 99.61 % | **99.89 %** | 99.89 % |
| *(대조) S6-2 순위 손실 모델* | *0.918* | *1.135* | *1.100* |
| *(대조) canonical* | *1.232* | *1.178* | *1.012* |

**확인: val 에서 특성 충돌이 막는 regret 은 0.00034 m 다. 모델의 regret 은
1.135 m 다 — 0.03 % 다.** 비퇴화 그룹의 **99.89 %** 는 충돌이 있어도 top-1
선택에 아무 지장이 없다 (충돌한 두 후보의 라벨이 같거나, 충돌하지 않는
다른 후보가 최소값을 갖거나).

**추론: (a) 특성 충돌은 canonical 을 못 이기는 원인이 아니다.** 특성 안에
정답을 고를 정보가 이미 들어 있다.

## 4. D1-3 — canonical 과 충돌의 관계

| | train | val | test |
|---|---:|---:|---:|
| canonical(`mode_idx=0`)이 낀 충돌 쌍 수 | 51 | 18 | 14 |

**확인: canonical 은 특별한 위치를 갖지 않는다.** 그룹의 0.9~1.4 % 에서만

때문이지, 토큰이 canonical 을 특별히 잘 보여주기 때문이 아니다).

## 5. D2 — 용량 축소 대조군 (학습 1회)

`scripts/diag_smallcap.py` 가 `learn.model.ModeScorer` 의 기본 용량만 프로세스
안에서 바꿔 끼우고 **S6-2 와 같은 `learn/train.py`·`learn/evaluate.py` 를 그대로
호출한다** (learn/ 를 수정하지 않기 위한 방식). 손실·데이터·split·시드·
lr·batch·patience 는 S6-2 의 `ranking` 실행과 동일하다.

| | S6-2 ranking | **smallcap** |
|---|---:|---:|
| d_model / 층 | 128 / 3 | **32 / 1** |
| 파라미터 | 434,948 | **24,260** (18배 축소) |
| best epoch | 10 | **37** |
| val 총손실 | 4.2424 | **4.2386** |

| | tau-b train | tau-b val | **격차** | regret train | regret val | **격차** |

| **smallcap** | 0.2081 | 0.2020 | **+0.0061** | 1.150 | 1.159 | **+0.009** |

### 그런데 val/test 는 나아지지 않았다

| 비퇴화 regret (m) | val | test |
|---|---:|---:|
| S6-2 ranking (434k) | 1.135 | 1.100 |

| S6 A3 | 1.133 | 1.031 |
| λ_rank=0 대조군 | 1.061 | 1.076 |
| canonical | 1.178 | 1.012 |

| val tau-b | test tau-b |
|---|---|
| smallcap 0.2020 / ranking 0.1978 / 대조군 0.1981 / A3 0.1930 | smallcap 0.1883 / ranking 0.1910 / 대조군 0.1896 / A3 0.1769 |

**확인: 파라미터를 18배 줄여 과적합을 사실상 없앴는데 val·test 성능이 변하지

**추론: 과적합은 증상이지 원인이 아니다.** 용량이 남아 train 을 외웠던 것이
맞지만, 그 외움을 막아도 val 에서 새로 얻는 것이 없다.

## 6. 게이트 판정

| # | 게이트 | 결과 | 판정 |
|---|---|---|:---:|
| 1 | D1 충돌률 측정 완료 | §2 표 (train/val/test 전부) | **통과** |
| 2 | 사전 판정 규칙 적용 | 충돌 쌍 중 loss 다른 비율 **20.6 / 13.9 / 10.3 %** — 세 split 모두 **10 % 이상** | **(a) 확정** |

**규칙대로 (a) 를 확정으로 기록한다. 게이트를 고치지 않는다.**

**그러나 이 판정은 이번 측정과 모순된다** — 아래 셋은 전부 규칙 밖에서 잰
값이고, 셋 다 (a) 를 반박한다 (확인):

1. **특성-오라클 regret val 0.00034 m** vs 모델 1.135 m (§3). 충돌이 막는
   몫이 0.03 % 다.
2. **비퇴화 그룹의 99.89 % 에서 충돌이 top-1 선택에 지장을 주지 않는다** (§3).
3. **충돌 쌍은 전체 쌍의 0.24 % 다** (§2).

**규칙이 왜 이렇게 나왔는가 (추론):** 규칙의 분모가 "충돌 쌍"이라 **충돌이
얼마나 드문지를 볼 수 없다.** 충돌 쌍 자체가 0.24 % 인데 그 중 13.9 % 가
라벨이 다르다는 것은 "전체 쌍의 0.03 %" 라는 뜻이다. 사전 규칙을 정할 때
분모를 "전체 후보 쌍" 또는 "regret 에 실제로 영향을 준 그룹"으로 뒀다면
같은 데이터가 (a) 기각으로 판정됐을 것이다.

**규칙이 지시한 처방도 이 데이터에는 맞지 않는다 (확인).** 규칙은
"처방은 mode 디코드 정보를 토큰에 추가하는 것"이라 했는데, §1 에서
**mode 문자열의 4개 필드는 이미 전부 토큰에 실려 있다.** 실제로 빠진 것은
mode 필드가 아니라 **클러스터 밖 에이전트의 route/rank** 이고, 그것을 넣어도
§3 의 상한 때문에 regret 은 최대 0.00034 m 밖에 못 줄인다.

## 7. 그래서 무엇이 남았는가

| 원인 후보 | 이번 단계의 증거 | 판정 |
|---|---|---|
| **(a) 특성 충돌** | 오라클 regret 0.00034 m, 99.89 % 그룹 무영향 | **반박됨** (규칙 판정은 §6 대로 (a) 확정) |
| **(b) 표본/용량** | 18배 축소로 격차 0.218 → 0.009 m, **val 이득 0** | **과적합은 증상, 원인 아님** |
| **(c) 표현 (새로 떠오른 것)** | 아래 | **가장 그럴듯함 (추론)** |

**(c) 추론의 근거:** 특성 안에 정보는 있다(오라클 ≈ 0). 그런데 그 정보는
**장면 안에서만** 쓸 수 있는 형태다 — `route` 원핫은 "이 에이전트의 몇 번째
경로냐"라는 **색인**일 뿐, 그 경로가 어디로 도는지·얼마나 긴지·다른
에이전트의 경로와 어디서 만나는지를 담지 않는다 (`token_field_audit.md`).
`routes[i]=1` 의 뜻은 에이전트마다 장면마다 다르다. 그래서

- 그룹 안에서 조회표를 외우는 것은 가능하고 (train tau-b 가 실제로 올랐다,
  S6-2 §6),
- 장면을 건너 일반화할 근거는 없으며 (val tau-b 가 안 올랐다),
- 용량을 줄이면 외우기가 막힐 뿐 일반화가 생기지는 않는다 (§5).

세 관찰이 전부 (c) 와 맞는다. **다만 이번 단계는 (c) 를 직접 검증하지
않았다** — route 의 기하(길이, 클리어런스, 교차점 등)를 토큰에 넣어 보는 것은
다음 단계의 일이고, 지시서대로 코드를 고치지 않았다.

## 8. 예상과 달랐던 것

1. **사전 규칙과 실제 영향이 반대 방향으로 나왔다.** 충돌 쌍 중 라벨이 다른
   비율은 문턱을 넘는데, 그 충돌이 막는 regret 은 0.03 % 다. 규칙의 분모
   문제였다 (§6).
2. **충돌의 100 % 가 클러스터 밖 에이전트 때문이다.** route 색인 잘림(0건)이나
   mode 디코드 누락(0건)이 아니다.
3. **지시서가 든 mode 필드(속도 프로파일 A/B/C, 횡 오프셋 폭)가 구현에 없다.**
   계획서 §3.2 와 `planning/worldmodel.py` 가 다르다.
4. **용량을 18배 줄였더니 train↔val 격차가 거의 사라졌는데 val 이 그대로다.**
   S6 §11 이후 계속 "과적합"으로 설명해 온 것이 실은 설명이 아니었다.
5. **smallcap 이 test 에서 ranking 보다 낫다** (1.026 vs 1.100, 유의성은
   재지 않았다 — 이번 단계의 게이트가 아니다). 세 모델이 여전히 canonical
   주변에서 서로 구별되지 않는다.

## 남은 불확실성

- **(c) 표현 가설을 직접 검증하지 않았다.** route 의 기하를 토큰에 넣는
  실험이 필요하고, 그것은 특성 축을 바꾸는 일이라 이번 단계 밖이다.
- **D2 는 크기 하나만 봤다** (지시서 지정). d_model 32/1층에서 격차가
  닫혔다는 것이지, 그 사이 어디에 최적이 있는지는 모른다.
- **smallcap 의 val/test 차이에 유의성 검정을 하지 않았다.** 이번 단계는
  방향만 보는 진단이다.
- **충돌 통계는 dedup 이후 CSV 기준이다.** `dedup_key` 는 구성원 위치와
  **전체 mode 문자열**로 만들어지므로(`collect_progress_labels.py:163`),
  토큰이 같은 후보는 dedup 대상이 아니었다 — 즉 이 충돌은 dedup 이 만든 것이
  아니다 (확인).
