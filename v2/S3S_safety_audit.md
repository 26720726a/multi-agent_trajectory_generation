## 2. S-1 — 침범 판정의 단일 출처

침범을 아는 경로가 셋이었고(`status`, `valid`, 두 clearance 열) 서로 다른 답을
냈다.  `safety/validate.py` 를 **유일한 출처**로 삼고, 그 판정을 CSV 에 그대로
옮겨 적는다.

`bench/run.py::FIELDS` 에 다섯 열을 더했다.

| 열 | 무엇 |
|---|---|
| `n_agent_violations` | 검증기의 에이전트 쌍 위반 수 — **판정 근거** |
| `n_obstacle_violations` | 검증기의 장애물/벽 위반 수 — **판정 근거** |
| `min_agent_clearance` | 같은 검증기의 최소 여유 (6자리) |
| `min_obstacle_clearance` | 같은 검증기의 최소 여유 (6자리) |
| `first_violation_t` | 처음 침범한 타임스텝.  없으면 −1 |

### 2-1. `status` 덮어쓰기는 고치지 않았다

지시서대로 별도 축으로 남겼다.  대신 **새 열이 덮어쓰기를 견디는지** 테스트로
확인한다.  `bench/run.py` 는 이렇게 동작한다.

```python
_fill(r, ...)                       # rep.valid 가 False 면 status = "invalid"
...
if not res.traj.feasible:
    r["status"] = f"unfinished:{res.note}"      # <- 덮어쓴다
```

`test_violation_columns_survive_the_status_overwrite` 가 실제 침범 궤적으로
`_fill` 을 부른 뒤 덮어쓰기를 재현하고, 판정 열이 남아 있는지 본다.

### 2-2. `first_violation_t` 는 계측이지 판정이 아니다

`safety/validate.py` 의 `Report` 에 필드를 더하고, 기존 루프에서 시점만
기록한다.  **판정 로직은 건드리지 않았다** — 위반 여부와 개수는 원래 세 필드가
그대로 정하고, 이 값은 "어디를 들여다볼 것인가" 를 가리킬 뿐이다.
§4 의 재판정이 그것을 확인한다 (같은 궤적에서 위반 수가 예전 결과와 일치).

## 3. S-2 — 판정 기준과 여유

| 대상 | 하한 | 근거 |
|---|---|---|
| 에이전트 쌍 | 중심거리 ≥ `min_sep(i,j)` = 0.70 | 계획서 §2.1 |
| 장애물·벽 | 중심~경계 ≥ `robot_radius` = 0.30 | 물리적 겹침 |

**여유는 1e-3 m 다.**

### 3-1. 지시서가 제안한 1e-6 은 쓸 수 없다

지시서는 "최소값이 0.7001 / 0.3200 이므로 1e-6 수준이면 충분해 보이나 확인하고
정하라" 고 했다.  확인해 보니 **안 된다.**

`bench/run.py::_fill` 이 clearance 를 `round(…, 4)` 로 기록한다.  반올림 오차가
최대 **5e-5** 이므로 1e-6 여유는 그 아래로 묻힌다 — 여유를 아무리 작게 잡아도
기록 정밀도가 판정을 흔든다.

### 3-2. 그래서 clearance 로 판정하지 않기로 했다

더 근본적인 해법을 골랐다.  **`validate.py` 가 이미 1e-3 여유로 판정하므로,
그 결과를 열에 적고 판정은 그 열로 한다.**  여유는 검증기 안에 **한 번만**
존재하고, 반올림은 판정 경로에서 사라진다.

새 clearance 열은 6자리로 적어 경계 근처에서도 값을 읽을 수 있게 했지만,
그것은 **얼마나 아슬아슬했는지**를 보는 용도이지 판정 근거가 아니다.

### 3-3. 1e-3 의 근거

원본 검증기가 쓰던 값이다.  `dt = 0.1 s` 에서 `v_max = 1.2 m/s` 이므로 한 스텝이
0.12 m 이고, 1e-3 은 그 **1/120** 이다.  부동소수 잡음보다 충분히 크고
물리적으로는 무시할 수 있는 폭이다.

여유가 실제로 경계를 가르는지는 `test_the_agent_threshold_sits_exactly_at_min_sep`
과 `test_the_obstacle_threshold_sits_exactly_at_the_radius` 가 하한 ±여유의
양쪽을 찔러 확인한다.

## 4. S-3 — 과거 배치 재판정

### 4-1. `git_commit` 만으로는 복원할 수 없었다

먼저 시도한 감사는 **현재 코드로 여섯 배치를 전부 재실행**했다.  그것은
재현이 아니라 다른 코드로 굴린 결과다 — 지시서가 짚은 그대로였고, 중단했다.

CSV 의 커밋 열을 보니 **모든 배치가 미커밋 상태에서 돌았다.**

| 배치 | CSV `git_commit` | CSV `phys_fp` | 복원에 쓴 커밋 |
|---|---|---|---|
| baseline_S2 | 445f7ff | 43ec5c75ad5c | `fb5c257` |
| A_amax3 | fb5c257 | 2070da06d4a0 | `3b72c4b` |
| A2_braking | aca1a47 | **2070da06d4a0** | `1c5a2bc` |
| A3_brakedist | aa1574f | 058289b6e9fe | `88755d1` |
| A4_nogeom | 88755d1 | 1f9fc93a5969 | `88755d1` + `brake_lookahead=None` |
| B3_decel | **88755d1** | 34f7729fcabc | `18fe932` + `wipeout_decelerate=True` |

`git_commit` 은 "배치를 돌릴 때의 HEAD" 일 뿐 그때의 코드가 아니다.  그래서
**배치 직후 커밋**으로 `git worktree` 를 만들어 복원했다.

`A_amax3` 과 `A2_braking` 의 지문이 같은 것(2070da06d4a0)은 S3-A‴ §9-4 가
지적한 구멍이다 — 제동 항은 알고리즘이라 config 지문에 잡히지 않는다.
둘은 커밋으로만 구분된다.

### 4-2. `phys_fp` 로 복원을 검증했다 — 하나가 어긋났다

각 워크트리에서 `effective_fingerprint` 를 계산해 CSV 와 대조했다.
**다섯은 바로 일치했고 A⁴ 만 어긋났다** (`987f93051fbe` vs `1f9fc93a5969`).

원인: A⁴ 배치 당시 `wipeout_decelerate` 필드가 **아직 없었다.**  필드 존재
자체가 지문을 바꾼다 (동작은 `False` 라 같다).  A3 워크트리(`88755d1`)에
`brake_lookahead=None` 만 적용해 다시 만들자 일치했다.

**지문이 복원 검증에 실제로 쓰인 첫 사례다** (확인).  이것이 없었다면
"복원했다고 생각한 코드" 로 감사를 돌릴 뻔했다.

### 4-3. 방법 — 궤적은 각 시점 코드, 판정은 하나의 검증기

두 단계로 나눴다.

1. 워크트리에서 표본 행을 다시 굴려 **궤적만** `.npz` 로 덤프
   (`scripts/s3s_dump_traj.py`, 14 워커 병렬)
2. 현재 트리에서 그것을 읽어 **현재 `safety/validate.py`** 로 판정
   (`scripts/audit_safety.py`)

이렇게 해야 "코드가 달라서" 와 "검증기가 달라서" 가 섞이지 않는다.

표본은 배치마다 **무작위 200행 + `min(agent_clr, obst_clr)` 하위 50행** 이다.
하위 50 은 경계에 가장 가까운 것들이라, 어긋남이 있다면 거기서 나온다.
(처음에는 `obstacle_clearance` 만으로 하위를 뽑았다가 지시서대로 두 값의
최솟값으로 고쳤다 — 에이전트 쪽 경계 사례를 놓칠 수 있었다.)

덤프 1,490행 전부 성공, 오류 0.

### 4-5. 그래서 어떻게 쓰는가

지시서의 "어긋남이 없는 경우" 경로다.  **표본 기반이므로 "전수 검증" 이 아니라

표본이 경계 쪽으로 치우쳐 있다는 점이 이 결론을 강하게 만든다 — 하위 50행은
가장 아슬아슬한 것들이고, 거기서도 두 방법이 갈리지 않았다.

## 5. S-4 — 침범 탐지 테스트 (게이트 2)

**"0건" 이 *안 일어났다* 인지 *못 잡는다* 인지 구별하려면 고의로 침범해 봐야
한다.**  `tests/test_violation_detection.py` 10종, 전부 통과.

| 확인 | 방법 |
|---|---|
| 에이전트 0.5 m 접근 | 하한 0.70 미만 — 잡는다 |
| 에이전트 경계 | 0.70 + 1e-4 / −여유/2 / −2×여유 로 세 지점을 찔러 정확히 갈리는지 |
| **샘플 사이 스쳐 지나감** | 끝점은 0.6 m 인데 스텝 중간에 겹침 → 스윕 최근접 0 을 잡는다 |
| 장애물 관통 | 사각형 한가운데 통과 |

## 6. S-5 — 안전 계층 커버리지 (`safety/README.md`)

핵심은 **두 장치의 성격이 다르다**는 것이다.

| 무엇을 | 누가 | 언제 | 성격 |
|---|---|---|---|
| 에이전트 간 충돌 | `_project_safe` | 후보 선택 **뒤** | **사후 투영** — 무엇이 오든 받아서 고친다 |
| 장애물·벽 충돌 | `free_steps` | 후보 선택 **전** | **사전 배제** — 안전한 것만 고르게 한다 |

`_project_safe` 에는 `Rect` 도 `scene` 도 인자에 없다.  장애물을 막는 것은
하드 필터 하나뿐이고, **전멸 fallback 은 그 필터 바깥에 있다.**  현재는
`v_cmd = 0` 이라 위치가 그대로여서 안전하지만, 거기서 조금이라도 움직이면
아무도 막지 않는다 — S3-B3 가 그것으로 88행을 깨뜨렸다.

문서와 테스트를 서로 참조시켰다:
`test_the_safety_projection_does_not_cover_obstacles` 가 소스에서 직접
`Rect`/`obstacle` 이 없음을 확인하고, README §2 가 그 테스트를 가리킨다.

`vo.py` 가 **soft** 라는 점도 적었다 — 이웃은 하드 필터에 없으므로 후보 전멸의
원인이 될 수 없고, S3-A″ §3-3 이 실측으로 확인했다 (전멸 시점 이웃 거리
중앙값 3.08 m).

## 7. S-6 — 게이트 문구

S3 이후 모든 단계의 "충돌 0건" 은 다음을 뜻한다.

```
n_agent_violations == 0  AND  n_obstacle_violations == 0
(tests/test_violation_detection.py 가 통과하는 파이프라인에서 측정)
```

`scripts/summarize_run.py` 를 그렇게 고쳤다.  판정 열이 없는 옛 CSV 는
clearance 로 물러나되 **판정 근거를 출력에 함께 적는다** — 지금 여섯 배치가
전부 그 경우이므로, 어떤 기준으로 나온 숫자인지가 눈에 보인다.

```
  충돌률     1.81%   (88행)      <- deadlock  42.14% (2048행) 과 함께 읽을 것
    에이전트 간 0행,  장애물/벽 88행
    판정 근거: clearance 열 (여유 0.001) — 이 CSV 에는 판정 열이 없다 (S3-S 이전 스키마)
```

충돌률은 계획서 §7.4 대로 **언제나 deadlock 과 짝으로** 낸다.

## 8. 예상과 달랐던 것

### 8-1. 결과는 옳았지만 게이트는 무효였다 — 그렇게 기록한다

§4-4 가 A⁴ 까지 침범 0 을 확인했다.  **그러나 S3-A ~ A‴ 당시의 "충돌 0건"
판정은 여전히 무효다.**  그 게이트들은 항상 0 이 나오는 열(`status == "invalid"`)
을 보고 통과했고, 만약 그때 침범이 있었다면 **똑같이 통과했을 것이다.**

**운이 좋았던 것이지 검증된 것이 아니었다.**  검증된 것은 지금이다.

이것은 논문 §7.1 KPI 의 신뢰성에 직접 관계된다.  "충돌률 0.0%" 를 주장하려면
그 숫자를 낸 장치가 침범을 잡을 수 있다는 것이 먼저 보여야 하고, 그 증거가
§5 다.  S3-A~A‴ 시점에는 그 증거가 없었다.

### 8-2. 지시서가 제안한 여유 1e-6 이 쓸 수 없었다

기록 정밀도(`round(…, 4)`, 오차 5e-5)가 여유보다 크다.  "최소값이 0.7001 이니
1e-6 이면 충분" 이라는 추론은 **기록된 값이 정확하다는 가정**에 기대고 있었다.
판정을 clearance 에서 떼어내는 것으로 문제 자체를 없앴다 (§3-2).

### 8-3. `git_commit` 이 코드 상태를 가리키지 않았다

여섯 배치 전부 미커밋 상태에서 돌았다.  CSV 의 커밋 열은 "그때의 HEAD" 이지
"그때의 코드" 가 아니다.  **배치 직후 커밋**으로 복원해야 했고, 그마저도
A⁴ 는 필드 하나 차이로 어긋나 `phys_fp` 대조로 잡았다 (§4-2).

배치를 돌리기 **전에** 커밋하는 습관이 없으면 재현이 이렇게 번거로워진다.

### 8-4. 두 방법이 한 건도 안 갈렸다

솔직히 몇 건은 갈릴 것으로 예상했다 — 특히 스윕 사례에서 clearance 열이
놓쳤을 가능성을 지시서도 우려했다.  1,490행에서 0 건이다.

**추론**: `agent_clearance` 열이 이미 `validate` 의 스윕 결과를 받아 적은
값이기 때문이다.  즉 (a)와 (b)는 "같은 검증기의 출력을 언제 읽었는가" 만
다르다.  독립적인 두 측정이 아니었다 — 그래서 일치가 당연하고, 이 대조가
확인해 준 것은 **"기록된 값이 그때의 검증 결과와 같다"** 는 것이지
"검증기가 옳다" 가 아니다.  후자를 확인하는 것은 §5 의 탐지 테스트다.

### 8-5. 열을 더하자 관계없는 테스트가 깨졌다

`test_a_half_written_last_row_is_dropped_and_reported` 가 "마지막 20바이트를
자르면 행이 깨진다" 고 가정하고 있었다.  판정 열 5개를 더하자 행이 길어져
20바이트를 잘라도 유효한 행으로 파싱됐다.  **잘라내는 양을 행 길이에
비례하게** 고쳤다.  테스트 픽스처가 스키마에 암묵적으로 의존한 자리다.
