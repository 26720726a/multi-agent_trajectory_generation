## 2. 왜 멈췄는가

S3-A 게이트 4 는 "성공률이 기준선 대비 −5%p 이내" 였다.  실측은 **−7.30%p**
(87.84% → 80.53%) 다.

지시서의 원칙 그대로 처리했다.

* **게이트를 먼저 정하고 미달 시 멈춘다.  결과를 보고 게이트를 고치지 않는다.**
  −5%p 를 −8%p 로 늘리지 않았고, `a_max` 를 3.0 보다 큰 값으로 되돌리지도
  않았다.
* **결과를 먼저 보고하고 코드를 고치지 않은 채로 멈췄다.**  §6-2 가 원인으로
  지목한 "감속 프로파일 부재" 를 고치면 게이트를 통과할 가능성이 있지만,
  그것은 지시서가 S3-A 에서 허용한 범위(= `_candidates` 의 제한) 밖의
  알고리즘 변경이다.
* 빨간 테스트 3건(`tests/test_safety.py`, `crossing2`)도 고치지 않고 남겼다.
  결과에 맞춰 테스트를 무르는 일이기 때문이다.

전문과 수치는 `reports/S3A_amax.md`.  요약하면:

## 7. 다음에 정해야 할 것

`reports/S3A_amax.md` §7-2 의 선택지 표가 본문이다.  요지만 옮긴다.

확인된 사실:

1. **충돌은 0 이다.**  안전은 `a_max` 도입과 무관하게 성립한다.
2. **안전 투영이 `a_max` 를 넘기는 일은 사실상 없다** (26,784건 중 56건, 0.2%).
   §A-2 는 이 숫자가 크면 계획서 §2.3 의 `a_max` 산출을 재검토하라고 했는데,
   **재검토할 근거는 이 데이터에 없다.**
3. 손실은 전부 deadlock 이고, 뿌리는 (a) 후보 팬 붕괴 — 순항 중
   `|v|=1.2` 에서 도달 가능한 속력이 `[0.9, 1.2]` 뿐이라 **한 스텝에 멈출 수
   없다**, (b) `v_pref` 에 제동 항이 없어 자기가 지울 수 없는 속도를 낸다.
4. 그럼에도 **209건은 새로 풀렸다** — 가속 제한이 진동성 livelock 을 구조적으로
   막는 것으로 보인다 (추론, 미검증).

선택지는 다섯이고 (A1 제동 항 추가 / A2 상대 속도 팬 / A3 `dt` 절반 /
A4 `a_max` 상향 / A5 A 를 채택하지 않고 진행), **섞지 말고 하나씩 짝지은
비교로** 재야 한다.  A4 는 목표값을 결과에 맞춰 고치는 것이라 원칙에 반한다.

**A1 은 시도했고 게이트 3 을 −7.55%p 로 미달했다** (`reports/S3A2_braking.md`).
제동 항은 효율(makespan·`wait`·전환 횟수)을 유의하게 개선했지만 성공률은
움직이지 않았다 (−0.25%p, p=0.57).  후보 팬 표가 한 칸도 안 바뀌었고
(`_candidates` 를 안 건드렸으므로 당연하다), `max_accel` 의 최악값이 감속이
아니라 **기하 하드 필터의 강제 정지**에서 나온다는 것이 새로 확인됐다.
셋을 합치면 **팬 붕괴가 독립적인 원인**이라는 결론이 되고, 다음 후보로
**A2(SPEED_LEVELS 상대화)** 가 지목되었다.

**그런데 S3-A" 의 진단이 A2 를 배제했다** (`reports/S3A3_wipeout_diag.md`).
급정거형 전멸 717건 전부에서 **도달 가능 원반 안 500점이 하나도 자유롭지
않았고**(H2), 동시에 즉시 정지(v=0)는 100% 자유였다 — 안전한 속도는 있는데
`a_max` 때문에 한 스텝에 도달할 수 없다.  팬을 어떻게 바꿔도 원반 밖으로는
나갈 수 없으므로 **A2 는 이 자리에 무효다.**

진단이 가리키는 것은 더 좁은 처방이다.  순항에서 정지까지 4 스텝 = 0.18 m 가
필요한데 하드 필터는 1 스텝(0.12 m) 앞만 본다.  기하로 막힌 급정거형의
**100%** 가 그보다 좁은 여유(중앙값 0.015 m)에서 일어났고, 의존성 대기 쪽도
같은 구조다(한 스텝 전에만 감속 시작).  A' 의 제동 항은 **목표까지의 거리만**
보므로 이 자리를 건드리지 못했다 — 대상 거리를 "가장 가까운 하드 제약까지의
자유 거리" 로 넓히는 것이 측정이 가리키는 방향이다.

그리고 전멸은 실패와 실제로 연결된다: 난이도 층화 후 27개 층 중 23개(85%)에서
방향이 일관하고 층 가중 평균 **−12.44%p** 다.

**그 처방(제동 대상 확장)도 실패했다** (`reports/S3A4_brake_distance.md`).
게이트 3·4·5 를 모두 미달했고, A' 대비 makespan 짝지은 차이 중앙값이
**0.000s**, 성공률 p=0.67, 급정거형 전멸 −3.2% 다.  반사실 평가의 `b` 가
**여전히 0.0%** 라는 것이 직접 증거다 — 제동 항은 `v_pref` 를 줄일 뿐이고,
도달 가능 원반의 크기는 `a_max*dt` 로 고정이라 **원반을 넓힐 수 없다.**
진단(H2)은 맞았고 처방이 그 H2 를 겨냥하지 못했다.

원반 쪽을 건드리는 후보가 남았다: `dt` 절반(B1), 하드 필터의 다단계화(B2),
전멸 시 `a_max` 안에서 최대 감속(B3), `a_max` 상향(B4).  B4 는 목표값을
결과에 맞춰 고치는 것이라 원칙에 반한다.

**그 다음 B3(전멸 시 a_max 로 감속)도 실패했다** (`reports/S3B3_decel_fallback.md`).
사양(계획서 §3.3-7)과 구현의 어긋남 자체는 고쳐졌지만 — 전멸 위반 −99.9% —
**장애물/벽을 88행에서 침범**해 게이트 2 를 깼고 성공률도 80.31% → 57.86% 로
무너졌다.  구조적 이유가 있다: 전멸은 "후보가 전부 기하 필터에 걸렸다" 는
뜻인데 감속 fallback 은 그 필터를 우회해 계속 움직이고, `_project_safe` 는
**에이전트 간만** 다루므로 장애물은 아무도 막지 않는다.  되돌렸다.

그 과정에서 **충돌률 지표가 무효였다는 것이 드러났다** (§7).
그래서 S3-B 로 가기 전에 **S3-S(안전 검증 체계)** 를 먼저 세웠다
(`reports/S3S_safety_audit.md`) — 판정 열 5개, 고의 침범 탐지 테스트 10종,
과거 여섯 배치 1,490행 재판정(불일치 0).

남은 후보는 **B2(다단계 필터)** 다.  필요한 깊이는 이미 측정되어 있다 —
4 스텝 = 0.18 m.

부수적으로 확인된 것 하나: **착지 스냅은 문제가 아니었다.**  층화하면
많을수록 성공률이 높고(0건 42.5% vs 4-10건 87.9%, +46.86%p) 이는 역인과다 —
목표에 도착해야 스냅이 생긴다.  S3-A' 가 위반 총계의 39.4% 라는 이유로
문제로 본 것은 오독이었다.

지금 상태에서 S3-B 로 넘어가면 `a_max` 가 만든 −7.30%p 위에 `v_max=2.0` 의
효과가 겹쳐 **어느 쪽이 무엇을 했는지 가릴 수 없다.**  "한 번에 한 축만" 이
바로 그것을 막으려는 규칙이므로 멈춘 것이다.

## 7. 충돌률 지표가 무효였다 (S3-B3 에서 발견)

`scripts/summarize_run.py` 는 충돌률을 `status == "invalid"` 로 셌다.  그런데
`bench/run.py::run_instance` 가 검증 실패를 그렇게 표시한 **직후에** 완주
실패면 `status = "unfinished:..."` 로 덮어쓴다.  실제로 여섯 배치 전부에서
`status == "invalid"` 가 **0 행**이고 `valid == False` 인 행은 100% 가
`unfinished:deadlock` 이었다.

즉 **S3-A 부터 A 4차까지의 "충돌 0건" 판정은 항상 0 이 나오는 열을 본 것이다.**

`agent_clearance` / `obstacle_clearance` 로 다시 판정했다.

| 배치 | 에이전트 침범 | 장애물 침범 | `agent_clr` 최소 | `obst_clr` 최소 |
|---|---|---|---|---|
| baseline_S2 | 0 | 0 | 0.7001 | 0.3200 |
| A_amax3 | 0 | 0 | 0.7001 | 0.3200 |
| A2_braking | 0 | 0 | 0.7001 | 0.3200 |
| A3_brakedist | 0 | 0 | 0.7001 | 0.3200 |
| A4_nogeom | 0 | 0 | 0.7001 | 0.3200 |
| **B3_decel** | 0 | **88** | 0.7001 | **0.2436** |

**이전 판정의 결론은 옳았다** — A 4차까지는 실제로 충돌 0 이다.  그러나
지표가 무효였으므로 검증된 것이 아니라 운이 좋았던 것이다.  B3 가 처음으로
진짜 충돌을 냈고 그제서야 드러났다.

`summarize_run.py` 를 clearance 기반으로 고쳤고 에이전트/장애물을 나눠 낸다.
`bench/run.py` 의 status 덮어쓰기 자체는 CSV 스키마를 바꾸는 일이라 손대지
않았다 — `valid` 와 두 clearance 열이 이미 있어 분석 쪽에서 해결된다.

**S3-S 에서 이것을 제대로 세웠다.**  `safety/validate.py` 의 판정을 CSV 에
직접 적는 열 5개(`n_agent_violations`, `n_obstacle_violations`,
`min_agent_clearance`, `min_obstacle_clearance`, `first_violation_t`)를 넣고,
S3 이후의 "충돌 0건" 게이트를 `n_agent_violations == 0 AND
n_obstacle_violations == 0` 으로 못 박았다.  고의로 침범하는 궤적을 만들어
**지표가 실제로 잡는지** 확인하는 테스트 10종도 함께 세웠다 — 그것이 없으면
"0건" 이 *안 일어났다* 인지 *못 잡는다* 인지 구별할 수 없다.

과거 여섯 배치를 각 배치의 코드 상태로 되살려(`phys_fp` 로 복원을 검증) 궤적을
다시 굴리고 **현재 검증기 하나로** 판정했다.  1,490행 표본에서 두 방법이
**한 건도 어긋나지 않았고**, A 4차까지 침범 0 이 확인됐다.

다만 **결과가 옳았다고 해서 당시의 게이트가 유효했던 것은 아니다.**  그때의
판정은 항상 0 이 나오는 열을 봤고, 침범이 있었더라도 똑같이 통과했을 것이다.
운이 좋았던 것이지 검증된 것이 아니었다 — 논문 §7.1 의 "충돌률 0.0%" 를
주장하려면 이 구별이 필요하다.
